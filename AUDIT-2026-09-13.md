All four apps were installed, built, served as **production builds**, crawled route by route
at 390 px and 1440 px, and then clicked through end to end as three real user journeys.
Everything below was found by running the product, not by reading it.

**Where the work happened:** a Linux sandbox with a working `pnpm` and a headless Chromium.
That matters, because it is the first time this codebase has ever been through a real
`install → typecheck → lint → build → run` cycle. The previous session's own notes said
FE-03 through FE-11 had never been built, and flagged that as "the main risk sitting in the
code right now". It was.

## The eight that actually mattered

**1. Every English page was served in Hindi.** `app/layout.tsx` called `getLocale()`, which
during static generation resolves *before* the child layout's `setRequestLocale()`. 35 of 62
routes shipped `lang="hi"` and Hindi `<title>`s to English visitors. `/legal/terms` on the
English site read "सेवा की शर्तें". Fixed by moving `<html>`/`<body>`/metadata into
`app/[locale]/layout.tsx`, where the locale is a real param, and making the root layout a
pass-through. `app/not-found.tsx`, `app/error.tsx` and a new `app/global-error.tsx` render
their own document shells.

**2. The buy flow dead-ended one click after "Continue to Pay".** `/checkout/<new order>`
answered **404** for every order the product itself had just created. Next.js bundles a
Server Action and the page that renders its result separately, and each bundle got its own
copy of the mock store — so the order `createOrder` pushed did not exist for the `getOrder`
in the page. The store is now pinned to `globalThis`. This one bug made the demo unusable
and would have survived to the real backend as the same singleton mistake.

**3. `/book` — the most important page in the product — looked broken.** Steps 2, 3 and 4
rendered only once a zone was selected, so a first-time visitor saw a zone map, three cards
and a screen of white space. The zone map itself drew **solid black rectangles**, because
`${color}33` built `hsl(var(--zone-vip))33` — invalid CSS, which SVG resolves to black — and
its labels were positioned at `y="NaN"` from a broken path-string parse. Rewritten to a
rect-based `ZoneMap` with `hsl(… / α)` fills, and the page now shows the full four-step
scaffolding with real prompts from the moment it loads.

**4. The language switcher printed mojibake.** `àª—à«` / `à¤¹à¤¿` — double-encoded UTF-8,
sitting in the header of every page. 40 files carried BOMs and/or double-encoded text. All
repaired; the switcher reads ગુ / હિ.

**5. The night lineup was unreadable.** Each card painted the night's theme colour and wrote
the label on top: Night 1 "White Night" was white-on-white and literally invisible, Nights 8
and 9 barely better. Now scrimmed, with the foreground derived for contrast.

**6. The marketing landing page was half-empty in all three languages.** 84 message keys the
page asked for had never been written — the entire how-it-works, proof, preview and FAQ
story. Written, in English, Gujarati and Hindi.

**7. Fonts came from Google at build time**, which is why the build could not run without
outbound network access. Now self-hosted from `@fontsource-variable` — faster first paint,
no third-party origin, and CI-safe.

**8. `pnpm-workspace.yaml` contained `esbuild: set this to true or false`** — a literal
placeholder that failed `pnpm install`. That alone blocked every build.

## Demo mode — verification bypassed, UI intact

Nothing waits on a backend, and every bypass says so on screen rather than silently
accepting anything. Shared strings live in `Common.demoMode` / `demoBadge` / `demoOtpHint` /
`useDemoCode`, in all three languages.

| Where | What happens |
|---|---|
| `/auth/start`, `/checkout` | "Use demo number" fills 98250 11001 |
| `/auth/verify`, `/checkout`, `/register/verify` | Segmented OTP, "Use demo code", auto-advance on the 6th digit |
| `/register/verify` details | "Fill demo details" loads a plausible Ahmedabad samiti |
| Scanner `/login` | The valid gate code is shown on screen, with a one-tap fill |

Also fixed: `/auth/profile`'s "Skip for now" used to drop the visitor into `/me` without ever
setting `isAuthenticated`. `confirmPhone()` now makes the session real at the OTP step, where
it belongs — including after checkout, so a buyer is signed in afterwards.

## The three journeys, verified by script

Re-runnable: `node /home/claude/audit/flows.mjs <out-dir>` with the four apps served.

1. **Attendee** — home → Book Passes → zone → pass type → quantity → Continue to Pay →
   checkout → OTP → Pay → confirmation with a real scannable QR → My Passes → pass detail.
2. **Organizer** — marketing home → Register → phone → OTP → event details → submit →
   application status → provisioned hand-off.
3. **Gate staff** — scanner → sign in with the gate code → scan screen → manual code entry →
   verdict → scan log.

## What is still open

- **Legal pages are starter content.** `/legal/{privacy,terms,refund-policy}` need a real
  review before anyone sells a ticket against them.
- **CSP is Report-Only**, deliberately: the apps inject an inline theme script before paint,
  and enforcing needs a per-request nonce. Flip it when this renders behind a server.
- **The mock store is per-process.** Four apps, four Node processes, four stores — approving
  a tenant in the dashboard is not visible to the marketing app. Only a real database fixes
  that; `globalThis` fixed the *within*-app half, which is what broke checkout.
- **No event photography.** The hero, night tiles and zone art are generated from CSS/SVG.
  They hold up, but real images will beat them.
- **`apps/web/middleware.ts`** now just re-exports `src/middleware.ts` so the two cannot
  drift. Safe to delete outright.
- Scanner pages still render mostly client-side. The shell is server-rendered now, but a
  gate phone on a bad connection would be better served by more of it.
